# Прецедент «Линтинг документа»
## Как я вижу поток данных линтинга

### Шаг 1. Пользователь инициирует проверку
Через UI (`AppContext` → `Renderer`) вызывается метод документа, например:
```
Document.runLint(): LintResult
```

### Шаг 2. Document собирает актуальный текст
`Document` знает своё текущее содержимое (буфер в памяти). Он извлекает из него **только проверяемый текст**:

- отбрасывает разметку Typst (`#let`, `#show`, код в блоках ` ``` `, математику `$...$`);
- оставляет естественный текст;
- сохраняет **карту смещений**: позиция в «чистом тексте» → позиция в исходном документе.

Это критично, потому что линтер работает с текстом без разметки, а ошибки нужно подсветить в исходном документе.

### Шаг 3. Вызов Linter
```
interface Linter {
LintResult check(String plainText, LintOptions options)
}
```

`TextLinter` внутри использует конкретный движок (Hunspell / LanguageTool / собственный словарь). Возвращает структуру:
```
LintResult {
    List<LintError> errors // Список ошибок внутри которого лежит структура LintError
    boolean success
    String errorMessage // если success = false (возникла ошибка)
}

LintError {
    int start, end
    String word
    String message // описание, например: "озможная опечатка"
    List<String> suggestions
}
```

### Шаг 4. Document сохраняет диагностику в контексте
`Document` **не меняет текст** (спец. требование: «Обнаружение ошибок не должно автоматически изменять содержимое документа»). Он лишь сохраняет `LintResult` в поле вида `List<LintError> diagnostics` и транслирует позиции из plainText обратно в координаты исходного документа через карту смещений.

### Шаг 5. UI подхватывает изменение
`AppContext`/`Renderer` наблюдает за состоянием `Document` (наблюдатель / событие `documentChanged`). При появлении диагностики:

- подсвечивает участки (подчёркивание);
- в панели показывает список ошибок и варианты исправления.

### Шаг 6. Пользователь выбирает ошибку → исправление
UI вызывает:
`Document` заменяет фрагмент **в оперативной памяти** (спец. требование: изменения сначала только в RAM), обновляет карту смещений и **инициирует повторную проверку**

### Расширения в моей модели
- **5а (ошибок нет):** `LintResult.errors.isEmpty()` → UI показывает «Ошибок не найдено».
- **5б (сбой линтера):** `success = false` → `Document` сохраняет `errorMessage`, UI уведомляет, редактирование не блокируется (спец. требование: недоступность проверки не препятствует редактированию).
- **8а (клик по подсветке):** UI передаёт в `Document` позицию клика → `Document` находит ближайшую ошибку по диапазону → возвращает её описание.
- **13б (Пропустить):** UI просто закрывает попап, `Document` ничего не меняет. Опционально — «пропущенные» ошибки можно хранить в сессии, чтобы не показывать повторно.

## 3. Разделение ответственности

| Компонент | Ответственность |
|---|---|
| `AppContext` | Владеет `Document`, связывает его с `Renderer`, маршрутизирует команды пользователя |
| `Document` | Хранит текст и диагностику, извлекает plainText, маппит позиции, применяет фиксы, инициирует перепроверку |
| `Linter` (интерфейс) | Контракт: «дай текст — верни ошибки» |
| `TextLinter` | Реализация: конкретный движок проверки орфографии |
| `Renderer` / `TypstCLI` | Отрисовка документа и подсветки |
| `TypstLSP` | Отдельно — синтаксис/семантика Typst (не путать с орфографией!) |

**Важное архитектурное решение:** орфография (`Linter`) и синтаксис Typst (`TypstLSP`) — **разные сервисы**. Это напрямую следует из спец. требования: «Проверка должна быть ориентирована на орфографию естественного языка, а не на синтаксис Typst». Смешивать их в одном модуле — ошибка.

## 4. Как я отвечаю на открытые вопросы (моё видение)

1. **Автоматически или по запросу?** — Гибрид: фоновая проверка с debounce (например, через 500 мс после паузы в вводе) + явная команда «Проверить документ». Так пользователь не ждёт и не раздражается от постоянных перерисовок.
2. **Языки?** — Стартуем с одного (русский/английский), но `Linter` проектируем с `language` в `LintOptions`, чтобы добавлять словари без изменения `Document`.
3. **Отделение кода от текста?** — Парсер Typst (или лёгкий токенизатор) в `Document` строит карту «текстовых» диапазонов; линтеру отдаётся только они. Это часть ответственности `Document`, а не `Linter`.
4. **Контекст предложения?** — Начинаем с проверки отдельных слов (проще, быстрее, предсказуемее). Контекстную проверку можно добавить как отдельную реализацию `Linter` (например, `LanguageToolLinter`), не меняя архитектуру.
