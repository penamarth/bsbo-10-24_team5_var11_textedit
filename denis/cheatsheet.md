## 1. Диаграмма прецедентов (use case diagram)

**Что это:** карта возможностей системы — «кто и что может делать». Отвечает на вопрос «что система умеет», не «как устроена».

**Элементы:**
- **Актор (человечек)** — внешняя сущность, взаимодействующая с системой. У нас: `Пользователь` (основной), `Typst CLI` и `Typst Language Server` (вспомогательные — система сама к ним обращается). Важно: внешние программы — тоже акторы.
- **Прямоугольник** — граница системы. Внутри — то, что пишем мы; снаружи — чужое.
- **Овал** — прецедент: законченная задача с целью и результатом с точки зрения пользователя (не функция кода!). Линия актор–овал = «инициирует/участвует».

**Наши прецеденты:** управление документами, линтинг, автоформатирование, просмотр Typst-документа, интеллектуальная поддержка Typst.

**Зачем две версии:** простая — обзор для заказчика; расширенная — прецеденты разбиты на атомарные операции по пакетам (Управление документами / Обработка текста / Поддержка Typst).

**Сказать преподу:** «Диаграмма показывает границы системы и её возможности. Основной актор — Пользователь, инициирует все прецеденты; Typst CLI и Language Server — вспомогательные акторы, к которым система обращается для компиляции и подсказок.»

**Каверзки:** «Почему Typst CLI — актор?» → любая внешняя сущность вне границы системы. «Чем прецедент отличается от функции?» → цель пользователя целиком, может включать десятки функций.

## 1.5. Ключевое различие: линтинг vs форматирование vs Typst

Три «проверяющих» сервиса, которые легко путаются:

| | `TextLinter` (ллинтинг) | `TextFormatter` (форматирование) | `TypstLSP` | `TypstCLIAdapter` |
|---|---|---|---|---|
| Что делает | Орфография обычного текста («програму») | Оформление: пробелы, пунктуация | Синтаксис языка Typst (`#let`, функции) | Компиляция typst → PDF |
| Результат | Список ошибок + варианты | Новый текст целиком | Подсказки, автодополнение | PDF или ошибки компиляции |
| Меняет текст сам? | Нет — предлагает, решает пользователь | Да — одной командой | Нет | Нет |
| Свой/внешний | Свой | Свой | Внешний сервер | Внешняя утилита |

**Пример:** в тексте `Я написал програму ,которая компилируеться. #unknwon_func()`
- TextLinter: «прогрАму», «компилируЕться» — опечатки
- TextFormatter: пробел перед запятой
- TypstLSP: `unknwon_func` — неизвестная функция Typst
- TypstCLIAdapter: соберёт PDF или вернёт ошибку компиляции

**Эвристика:** решение очевидно и безопасно применить ко всему тексту → форматирование; нужно спросить пользователя → линтинг; про синтаксис typst-разметки → TypstLSP/CLI.

## 2. Диаграмма классов

**Что это:** «из каких кирпичей построена система и как они связаны». Прямоугольник = класс (кусок кода с одной ответственностью), стрелки = отношения.

**Классы:**
- `AppContext` — сессия редактора («мозг»): какие документы открыты, что активно. Аналогия — окно VS Code.
- `Document` — один открытый файл: текст в памяти + метаданные (путь, диагностика). Аналогия — вкладка.
- `Renderer` — только отображает состояние на экран, ничего не хранит.
- `FileSystemAPI` — обёртка над чтением/записью файлов ОС.
- `Linter`, `Formatter` — интерфейсы (контракты); `TextLinter`, `TextFormatter` — их реализации.
- `TypstLSP` — адаптер к Typst Language Server; `TypstCLIAdapter` — адаптер к утилите `typst compile`.

**Стрелки:**
- `*──` композиция: «владеет, часть живёт внутри целого» (`AppContext *-- Document`: закрыл сессию — документы закрылись).
- `-->` ассоциация/зависимость: «использует, знает о» (`Document --> Linter`, `AppContext --> Renderer` — контекст командует рендерером).
- `..▷` реализация интерфейса: `TextLinter ..|> Linter`.

**Интерфейс vs реализация (розетка и прибор):**
- Интерфейс `Linter` = контракт «дай текст — верни LintResult». Кода нет, только сигнатура метода.
- `TextLinter` = конкретный проверяльщик со словарём, пишет настоящий код `check()`.
- Зачем: `Document` знает только «розетку». Подменяем `TextLinter` на `LanguageToolLinter` или фейк для тестов — `Document` не меняется. Паттерн **Стратегия**, принцип Open/Closed.

**Паттерны:** Стратегия (интерфейсы + реализации), Адаптер/Шлюз (`FileSystemAPI`, `TypstLSP`, `TypstCLIAdapter` — прячут внешний мир), разделение ответственности (данные / отображение / сервисы).

**Согласованность с прецедентами:** каждому прецеденту — стрелка: `→FileSystemAPI` управление документами, `→Linter` линтинг, `→Formatter` форматирование, `→TypstLSP` поддержка Typst, `→TypstCLIAdapter` просмотр.

**Сказать преподу:** «Архитектура вокруг AppContext — он владеет документами и командует рендерером. Document — информационный эксперт: хранит текст и делегирует сервисам. Орфография и форматирование за интерфейсами (Стратегия), внешние инструменты — в адаптерах. UI отделён от логики.»

## 3. Сценарии (описание прецедента)

**Что это:** развёрнутое текстовое описание прецедента по шаблону Лармана — мини-ТЗ на фичу, до кода, **языком заказчика** (без техжаргона: не «AppContext вызывает runLint()», а «система проверяет текст»).

**Структура:**
- **Рамки** — в какой системе происходит.
- **Уровень** — «задача пользователя».
- **Основной исполнитель** — кто запускает (Пользователь); бывает вспомогательный (внешний сервис).
- **Заинтересованные лица** — чьи интересы затронуты (думаем о людях, не о коде).
- **Предусловия** — что верно ДО (редактор запущен, документ открыт).
- **Постусловия** — что гарантированно стало верным ПОСЛЕ (ошибки выделены, исправления применены, файл на диске не изменён).
- **Основной успешный сценарий** — «счастливый путь», шаги чередуются «пользователь → система».
- **Расширения** — альтернативы. Номер = номер шага, где отклонение (`2а` = «на шаге 2 иначе»; `*а` = «на любом шаге»). Внутри — мини-сценарий: возвращается в основной поток или завершает прецедент.
- **Специальные требования** — нефункциональные, именно этого прецедента.
- **Открытые вопросы** — честные «ещё не решили» (не слабость, а зрелость анализа).

**Наши золотые спец. требования линтинга:** обнаружение ошибок не меняет текст автоматически; проверка — орфография, не синтаксис Typst; недоступность проверки не мешает редактированию; запись на диск — отдельная команда из «Управления документами» (связь между прецедентами!).

**Формула:** сценарий = ЧТО происходит (для заказчика), диаграмма последовательности = КАК внутри (для разработчика).

**Сказать преподу:** «Сценарий описывает взаимодействие на уровне цели пользователя: 5 шагов основного потока, расширения привязаны к номерам шагов. Технические детали вынесены в диаграмму последовательности и контракты операций.»

## 4. Диаграмма последовательности (sequence diagram)

**Что это:** «чат-переписка» объектов во времени — кто кому какие сообщения шлёт и в каком порядке. Время течёт сверху вниз.

**Элементы:**
- Линии жизни (вертикали) — участники; имена строго из диаграммы классов (согласованность!).
- Сплошная стрелка = вызов метода; пунктирная = возврат результата.
- Полоска активации — объект занят работой.
- `alt`-рамка = ветвление (if/else): ветки alt = расширения сценария.
- Жёлтые заметки = пояснения.

**Наша диаграмма, блок 1 «Проверка»:**
`lintDocument()` → `AppContext` (контроллер ловит событие) → `Document.runLint()` → `extractPlainText()` (выкинуть разметку Typst, построить карту смещений) → `TextLinter.check()` → `LintResult`. Дальше `alt`: сбой → уведомление; пусто → «ошибок нет»; есть ошибки → `mapPositions()` (пересчёт в координаты исходника!) → `Renderer.showDiagnostics` → подчёркивания.

**Блок 2 «Исправление»:**
`selectError(position)` → `getErrorAt` → `LintError` + варианты → попап. `alt`: `applyFix` → замена **в памяти** → повторный `check` → обновление отображения; или `skipError` → пометить пропущенной.

**Почему повторный check:** замена могла сдвинуть позиции или породить новую ошибку.

**Почему «в памяти»:** спец. требование — файл на диске меняется только отдельным сохранением.

**Правило согласованности:** стрелка на sequence-диаграмме существует только если есть связь на диаграмме классов. У нас: `AppContext→Document` (композиция), `Document→TextLinter` (через `Linter`), `AppContext→Renderer` (новая стрелка). Renderer не дёргает Document напрямую — он «чистый художник».

**GRASP-паттерны:** Controller (`AppContext` ловит события и делегирует), Information Expert (`Document` владеет текстом и сам делает extract/map/fix), Low Coupling (`Document` не знает про `Renderer`), Protected Variations (`TextLinter` за интерфейсом).

**Контракты операций** (`lint_document_operations.md`): каждая стрелка «актор → система» = системное событие, для него контракт: предусловия + постусловия тремя глаголами Лармана — *создание экземпляра*, *формирование ассоциации*, *модификация атрибута*. У нас 4 операции: `lintDocument()`, `selectError(position)`, `applyFix(errorIndex, suggestion)`, `skipError(errorIndex)`.

**Сказать преподу (за 40 секунд):** «Пользователь вызывает lintDocument() — контроллер AppContext делегирует Document. Документ как информационный эксперт извлекает текст без разметки, вызывает TextLinter через интерфейс Linter, пересчитывает позиции и возвращает результат; AppContext командует Renderer отрисовать диагностику. Ветки alt — расширения сценария. Второй блок — цикл исправлений с перепроверкой после applyFix. Каждому системному событию соответствует контракт операции.»

**Каверзки:**
- «TextLinter или Linter на диаграмме?» → участник конкретный (TextLinter), контракт — интерфейс Linter, реализацию можно подменить.
- «Чем отличается от блок-схемы?» → блок-схема — решения одного алгоритма; sequence — взаимодействие нескольких объектов, видно распределение ответственности.
- «Что если текст не сохранён?» → нормально: Document хранит текст в памяти, сохранение — отдельный прецедент.
- «Две ветки: ошибок нет и сбой — в чём разница?» → пустой список ошибок ≠ поломка сервиса; разные исходы, разная реакция UI.

## Быстрые ответы на «объясни за 30 секунд»

1. **Диаграмма прецедентов** — карта возможностей: кто (акторы) что (овалы) может делать в системе (прямоугольник-граница).
2. **Диаграмма классов** — кирпичи системы: AppContext владеет документами, Document делегирует сервисам, интерфейсы для подменяемости, адаптеры для внешнего мира.
3. **Сценарий** — ТЗ на одну фичу человеческим языком: предусловия → основной поток → расширения → постусловия.
4. **Диаграмма последовательности** — как объекты переговариваются во времени для выполнения одного сценария; плюс контракты операций = что гарантирует каждое событие.
