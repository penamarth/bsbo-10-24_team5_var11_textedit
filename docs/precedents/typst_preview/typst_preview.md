# Прецедент «Просмотр Typst-документа»

## Как я вижу поток данных предварительного просмотра

### Шаг 1. Инициализация и отслеживание изменений

Просмотр может запускаться как вручную пользователем (`AppContext → Renderer`), так и автоматически при изменении текста.

`Document.compileView(): PreviewResult`

### Шаг 2. Document передаёт буфер в памяти

Для компиляции несовершенных изменений `Document` предоставляет своё актуальное текстовое содержимое (буфер в памяти) без обязательного сохранения файла на диск (спец. требование: «не должно требоваться предварительное сохранение»).

### Шаг 3. Вызов компилятора через TypstCLI

Система делегирует задачу компиляции компоненту `TypstCLI`, который является обёрткой над внешним компилятором.

```java
interface TypstCompiler {
    PreviewResult compile(String documentText, CompileOptions options)
}
```

`TypstCLI` передаёт текст через стандартный ввод (`stdin`) или временный файл во внешний процесс `typst compile` и возвращает структуру:

```text
PreviewResult {
    byte[] pdfData      // Скомпилированный документ в бинарном виде (PDF или под рендер страниц)
    List<CompileDiagnostic> errors // Список ошибок компиляции, если они есть
    boolean success     // Флаг успешности компиляции
}

CompileDiagnostic {
    int line            // Строка ошибки в исходном коде
    int column          // Колонка ошибки в исходном коде
    String message      // Описание ошибки компиляции (например, "unknown variable")
}
```

### Шаг 4. Обновление контекста редактора

`Document` получает `PreviewResult`.

- При успехе: бинарные данные (`pdfData`) сохраняются в контексте редактора.
- При ошибке: `success = false`, данные документа не обновляются, но сохраняется список `errors` для вывода диагностики. Исходный текст в `Document` остаётся нетронутым.

### Шаг 5. UI динамически отображает результат

Модуль пользовательского интерфейса (`Renderer`), подписанный на события изменения состояния компиляции:

- При `success = true` — обновляет окно предварительного просмотра, рендеря полученные байты.
- При `success = false` — выводит панель с ошибками компиляции (лог ошибок), подсвечивая проблемные строки в редакторе кода.

## Расширения в моей модели

- **4а (При компиляции обнаружены ошибки):** `PreviewResult.success = false` и список `errors` не пуст. `Document` сохраняет полученную диагностику. `Renderer` не обновляет страницу просмотра (чтобы не показывать пустой экран или сломанную верстку), а выводит панель с логом ошибок компиляции и визуально маркирует строки с ошибками в коде. Редактирование не блокируется.
- **4б (Внешнее средство Typst CLI недоступно):** `PreviewResult.success = false`, список `errors` пуст, но заполнено поле `errorMessage` (например, `"Typst CLI not found in PATH"`). Система переводит модуль превью в режим ошибки. `Renderer` выводит системное уведомление о недоступности компилятора. Пользователь может продолжать писать текст, превью просто ждёт восстановления доступа к CLI.
- **7а (Пользователь закрывает предварительный просмотр):** `AppContext` посылает сигнал `Renderer` уничтожить или скрыть окно отображения. `Document` прекращает фоновые вызовы метода `compileView()` при изменении текста, экономя ресурсы процессора. Бинарные данные `pdfData` могут быть очищены из оперативной памяти.

## Разделение ответственности

| Компонент | Ответственность |
|---|---|
| `AppContext` | Владеет `Document`, управляет переключением режимов отображения (Split View / Только код / Только превью) |
| `Document` | Хранит исходный текст, предоставляет буфер для компиляции, фиксирует ошибки компиляции в своём контексте |
| `TypstCompiler` (интерфейс) | Контракт: «получи сырой текст Typst — верни скомпилированный байт-код или ошибки» |
| `TypstCLI` | Реализация: низкоуровневое взаимодействие с бинарным файлом `typst` через CLI, обработка `stdout`/`stderr` |
| `Renderer` | Отрисовка скомпилированного PDF-документа графическими средствами и вывод сообщений об ошибках компиляции |

**Важное архитектурное решение:** `TypstCLI` работает как «чистый» транслятор текста в визуальное представление. Он не занимается разбором логики и не хранит состояние редактора. Ошибки компиляции (синтаксис Typst, ненайденные функции верстки) обрабатываются строго здесь, в то время как орфография текста (`Linter`) и автодополнение кода в реальном времени (`TypstLSP`) остаются изолированными в своих модулях.

## Как я отвечаю на открытые вопросы (моё видение)

1. **Автоматически или по запросу?** — При открытии панели превью включается автообновление (Live Preview) с механизмом debounce (например, 700 мс после окончания ввода текста), чтобы не запускать тяжелый процесс компиляции на каждый нажатый символ.
2. **В каком формате передавать результат?** — В формате PDF (или потоком PNG-изображений страниц), который `Renderer` может отобразить в соседнем окне. PDF предпочтительнее, так как встроенный движок Typst компилирует в него мгновенно.
3. **Сохранять ли результат на диск?** — Нет, скомпилированный буфер превью хранится исключительно в оперативной памяти. Экспорт в готовый PDF-файл на диск — это отдельное явное действие пользователя («Экспорт»), не входящее в базовый просмотр.
4. **Синхронизация прокрутки (Sync Scroll)?** — Архитектура позволяет в будущем расширить `CompileOptions` для передачи координат курсора, чтобы превью автоматически скроллилось к нужной странице, где сейчас пишет пользователь. На первом этапе делаем параллельное статическое отображение.
