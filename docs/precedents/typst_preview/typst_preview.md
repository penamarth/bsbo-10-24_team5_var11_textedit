# Прецедент «Просмотр Typst-документа»

## Как я вижу поток данных предварительного просмотра

### Шаг 1. Инициализация и отслеживание изменений

Пользователь инициирует просмотр или редактирует текст через главный контроллер (`Пользователь → AppContext → Document`). При активной панели превью обновление запускается автоматически с небольшой задержкой (debounce).

`Document.CompileView() (PreviewResult, error)`

### Шаг 2. Document передаёт буфер в памяти

Для компиляции несохранённых изменений `Document` предоставляет своё актуальное текстовое содержимое (буфер в памяти) без обязательного сохранения файла на диск (спец. требование: «не должно требоваться предварительное сохранение»).

### Шаг 3. Вызов компилятора через адаптер TypstCLIAdapter

Система делегирует задачу компиляции компоненту `TypstCLIAdapter`, который реализует интерфейс `TypstCompiler` и служит обёрткой над внешней консольной утилитой `TypstCLI`.

```go
type TypstCompiler interface {
    Compile(documentText string, options CompileOptions) (PreviewResult, error)
}
```

`TypstCLIAdapter` запускает внешний процесс `typst compile` (через стандартный пакет `os/exec` с флагом `--format png`), передаёт ему текст через стандартный ввод (`stdin`), считывает результат и возвращает структуру (или системную ошибку выполнения `error`):

```go
type PreviewResult struct {
    Pages   [][]byte            // Скомпилированные страницы документа в виде изображений (PNG)
    Errors  []CompileDiagnostic // Список синтаксических ошибок компиляции, если они есть
    Success bool                // Флаг успешности компиляции документа
}

type CompileDiagnostic struct {
    Line    int    // Строка ошибки в исходном коде
    Column  int    // Колонка ошибки в исходном коде
    Message string // Описание ошибки компиляции (например, "unknown variable")
}
```

### Шаг 4. Обновление контекста редактора

`Document` получает `PreviewResult` (и системную ошибку `err`, если она возникла) и возвращает их в `AppContext`.

- **При успехе (`err == nil` и `Success == true`):** байты изображений (`Pages`) сохраняются в контексте документа.
- **При ошибке:** визуальные данные не обновляются, но сохраняется список `Errors` (или текст системной ошибки `err`) для вывода диагностики в терминале. Исходный текст в `Document` остаётся нетронутым.

### Шаг 5. TUI динамически отображает результат

`AppContext` передаёт полученный `PreviewResult` в модуль терминального пользовательского интерфейса (`Renderer`) с помощью вызова `RenderPreview(result)`:

- При `Success == true` — `Renderer` отрисовывает полученные изображения страниц прямо в TUI-панели терминала (используя графические протоколы терминала, такие как Kitty/Sixel, или ASCII/Unicode-аппроксимацию в качестве запасного варианта).
- При `Success == false` или наличии `err` — `Renderer` формирует виджет с логом ошибок компиляции (или уведомлением о недоступности CLI) и отображает их пользователю.

## Расширения в моей модели

- **4а (При компиляции обнаружены ошибки):** `err == nil`, но `PreviewResult.Success == false` и слайс `Errors` не пуст. `Document` сохраняет полученную диагностику. `Renderer` не обновляет область просмотра (чтобы не показывать пустой экран), а выводит TUI-панель с логом ошибок компиляции и визуально подсвечивает строки с ошибками в редакторе. Редактирование не блокируется.
- **4б (Внешнее средство Typst CLI недоступно):** Вызов `Compile` возвращает ненулевую системную ошибку `err != nil` (например, `exec.ErrNotFound`). Система переводит панель превью в состояние ошибки. `Renderer` выводит пользователю уведомление в статусной строке TUI о недоступности компилятора. Пользователь может продолжать писать текст.
- **7а (Пользователь закрывает предварительный просмотр):** `AppContext` посылает команду `Renderer.ClosePreview()` для скрытия TUI-панели отображения и перераспределения места в терминале. Фоновые горутины компиляции (`CompileView()`) при вводе текста останавливаются для экономии ресурсов процессора. Слайс байтов `Pages` очищается из оперативной памяти.

## Разделение ответственности

| Компонент | Ответственность |
|---|---|
| `AppContext` | Единая точка входа для команд и событий терминала; владеет `Document`, координирует вызов компиляции и передачу результата в `Renderer` |
| `Document` | Хранит исходный текст, предоставляет буфер для компиляции, фиксирует ошибки компиляции в своём контексте |
| `TypstCompiler` (интерфейс) | Контракт: «получи сырой текст Typst — верни слайс изображений страниц, ошибки компиляции или системную ошибку» |
| `TypstCLIAdapter` | Адаптер: изолирует логику работы с `os/exec`, запускает внешний `TypstCLI`, обрабатывает `stdin`/`stdout`/`stderr` |
| `TypstCLI` | Внешняя консольная утилита компиляции документов Typst |
| `Renderer` | Отрисовка скомпилированных страниц в TUI-фрейме средствами терминала и вывод виджетов с ошибками компиляции |

**Важное архитектурное решение:** Выделение интерфейса `TypstCompiler` и реализации `TypstCLIAdapter` полностью изолирует бизнес-логику `Document` от низкоуровневой работы с процессами операционной системы (`os/exec`). При этом сам компилятор отвечает строго за сборку документа и синтаксические ошибки Typst, в то время как орфография естественного языка (`Linter`) и автодополнение кода (`TypstLSP`) остаются в своих независимых модулях.

## Как я отвечаю на открытые вопросы (моё видение)

1. **Автоматически или по запросу?** — При открытии панели превью включается автообновление (Live Preview) с механизмом debounce (например, 700 мс после окончания ввода текста через `time.Timer`), чтобы не запускать тяжелый процесс компиляции на каждый нажатый символ.
2. **В каком формате передавать результат?** — В формате растровых изображений (PNG), так как терминал (TUI) не умеет нативно рендерить PDF-файлы. Встроенный движок Typst позволяет компилировать текст напрямую в PNG через `--format png`, который затем выводится в терминал через графические протоколы (Kitty/Sixel) или псевдографику.
3. **Сохранять ли результат на диск?** — Нет, скомпилированный буфер превью хранится исключительно в оперативной памяти (`[][]byte`). Экспорт в готовый PDF-файл на диск — это отдельное явное действие пользователя («Экспорт»), не входящее в базовый просмотр.
4. **Синхронизация прокрутки (Sync Scroll)?** — Архитектура позволяет в будущем расширить `CompileOptions` для передачи номера страницы или координат курсора, чтобы превью автоматически переключалось на нужную страницу, где сейчас пишет пользователь. На первом этапе делаем базовую постраничную навигацию в TUI.
