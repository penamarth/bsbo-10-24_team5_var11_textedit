# Прецедент «Просмотр Typst-документа»

## Как я вижу поток данных предварительного просмотра

### Шаг 1. Инициализация и отслеживание изменений

Пользователь инициирует просмотр или редактирует текст через главный контроллер (`Пользователь → AppContext → Document`). При активном окне превью обновление запускается автоматически с небольшой задержкой (debounce).

`Document.compileView(): PreviewResult`

### Шаг 2. Document передаёт буфер в памяти

Для компиляции несохранённых изменений `Document` предоставляет своё актуальное текстовое содержимое (буфер в памяти) без обязательного сохранения файла на диск (спец. требование: «не должно требоваться предварительное сохранение»).

### Шаг 3. Вызов компилятора через адаптер TypstCLIAdapter

Система делегирует задачу компиляции компоненту `TypstCLIAdapter`, который реализует интерфейс `TypstCompiler` и служит обёрткой над внешней консольной утилитой `TypstCLI`.

```java
interface TypstCompiler {
    PreviewResult compile(String documentText, CompileOptions options);
}
```

`TypstCLIAdapter` запускает внешний процесс `typst compile`, передаёт ему текст через стандартный ввод (`stdin`), считывает результат и возвращает структуру:

```text
PreviewResult {
    byte[] pdfData                 // Скомпилированный документ в бинарном виде (PDF)
    List<CompileDiagnostic> errors // Список ошибок компиляции, если они есть
    boolean success                // Флаг успешности компиляции
    String errorMessage            // Системное сообщение об ошибке (если сам CLI недоступен)
}

CompileDiagnostic {
    int line                       // Строка ошибки в исходном коде
    int column                     // Колонка ошибки в исходном коде
    String message                 // Описание ошибки компиляции (например, "unknown variable")
}
```

### Шаг 4. Обновление контекста редактора

`Document` получает `PreviewResult` и возвращает его в `AppContext`.

- **При успехе:** бинарные данные (`pdfData`) сохраняются в контексте документа.
- **При ошибке:** `success = false`, визуальные данные не обновляются, но сохраняется список `errors` (или `errorMessage`) для вывода диагностики. Исходный текст в `Document` остаётся нетронутым.

### Шаг 5. UI динамически отображает результат

`AppContext` передаёт полученный `PreviewResult` в модуль пользовательского интерфейса (`Renderer`) с помощью вызова `renderPreview(PreviewResult)`:

- При `success = true` — `Renderer` рендерит полученные байты PDF и возвращает пользователю визуальное представление готового документа.
- При `success = false` — `Renderer` формирует панель с логом ошибок компиляции (или уведомлением о недоступности CLI) и отображает их пользователю.

## Расширения в моей модели

- **4а (При компиляции обнаружены ошибки):** `PreviewResult.success = false` и список `errors` не пуст. `Document` сохраняет полученную диагностику. `Renderer` не обновляет страницу просмотра (чтобы не показывать пустой экран или сломанную верстку), а выводит панель с логом ошибок компиляции и визуально маркирует строки с ошибками в коде. Редактирование не блокируется.
- **4б (Внешнее средство Typst CLI недоступно):** `PreviewResult.success = false`, список `errors` пуст, но заполнено поле `errorMessage` (например, `"Typst CLI not found in PATH"`). Система переводит модуль превью в режим ошибки. `Renderer` выводит пользователю системное уведомление о недоступности компилятора. Пользователь может продолжать писать текст.
- **7а (Пользователь закрывает предварительный просмотр):** `AppContext` посылает команду `Renderer.closePreview()` для скрытия окна отображения и уведомляет пользователя об изменении интерфейса. Фоновые вызовы метода `compileView()` при вводе текста останавливаются для экономии ресурсов процессора. Бинарные данные `pdfData` могут быть очищены из оперативной памяти.

## Разделение ответственности

| Компонент | Ответственность |
|---|---|
| `AppContext` | Единая точка входа для команд пользователя; владеет `Document`, координирует вызов компиляции и передачу результата в `Renderer` |
| `Document` | Хранит исходный текст, предоставляет буфер для компиляции, фиксирует ошибки компиляции в своём контексте |
| `TypstCompiler` (интерфейс) | Контракт: «получи сырой текст Typst — верни скомпилированный байт-код или ошибки» |
| `TypstCLIAdapter` | Адаптер: изолирует логику работы с системными процессами, запускает внешний `TypstCLI`, обрабатывает `stdin`/`stdout`/`stderr` |
| `TypstCLI` | Внешняя консольная утилита компиляции документов Typst |
| `Renderer` | Отрисовка скомпилированного PDF-документа графическими средствами и вывод сообщений об ошибках компиляции |

**Важное архитектурное решение:** Выделение `TypstCLIAdapter` полностью изолирует бизнес-логику `Document` от низкоуровневой работы с процессами операционной системы. При этом сам компилятор отвечает строго за сборку документа и синтаксические ошибки Typst, в то время как орфография естественного языка (`Linter`) и автодополнение кода (`TypstLSP`) остаются в своих независимых модулях.

## Как я отвечаю на открытые вопросы (моё видение)

1. **Автоматически или по запросу?** — При открытии панели превью включается автообновление (Live Preview) с механизмом debounce (например, 700 мс после окончания ввода текста), чтобы не запускать тяжелый процесс компиляции на каждый нажатый символ.
2. **В каком формате передавать результат?** — В формате PDF, который `Renderer` может отобразить в соседнем окне. PDF предпочтительнее, так как встроенный движок Typst компилирует в него мгновенно.
3. **Сохранять ли результат на диск?** — Нет, скомпилированный буфер превью хранится исключительно в оперативной памяти. Экспорт в готовый PDF-файл на диск — это отдельное явное действие пользователя («Экспорт»), не входящее в базовый просмотр.
4. **Синхронизация прокрутки (Sync Scroll)?** — Архитектура позволяет в будущем расширить `CompileOptions` для передачи координат курсора, чтобы превью автоматически скроллилось к нужной странице, где сейчас пишет пользователь. На первом этапе делаем параллельное статическое отображение.
